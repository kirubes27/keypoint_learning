Verdict: BLOCK

The candidate has the right overall shape and several genuinely strong safeguards, but it does not yet enforce the stated authority chain end to end. Three P0 gaps allow a final evidence claim to diverge from the approved run or from what the finalizer actually executed:

“Approval” is currently only a set of committed file references, not a semantically validated approval of this manifest and implementation.

The runtime can evaluate a different strict test manifest while provenance names the approved test-pair artifact.

The final evidence receipt can be minted without consuming the one-shot evaluator path, and the one-opening guarantee is only process-local.

These are bounded engineering defects. They do not require reopening Task55 versus Task80, choosing an epoch rule, setting scientific thresholds, or inspecting banana/kettle data.

Violated semantic claim

A run is possible only under a committed manifest that was explicitly approved together with the implementation and decision records governing that run.

Concrete failure mode

A clean later commit could retain the same manifest and approval references. Alternatively, the same unrelated committed JSON or Markdown file could be referenced as the decision, both reviews, and approval. The validator would accept the file identities without establishing that:

the user approved the run;

the approval concerns this exact manifest;

the reviews concern this exact decision;

the approval covers the currently executing implementation.

The existing clean-tree and current-commit receipt fields should remain; they solve a separate provenance problem.

representation_fixed_final_runt…

Violated semantic claim

A final evidence receipt exists only if the exact authorized finalizer completed one held-out opening phase, one inference, and one provenance-validated descriptive evaluation.

Concrete failure modes

After obtaining a valid checkpoint capability, a caller can place arbitrary JSON files at the bundle/result paths and call write_evidence_receipt() with a fabricated ledger. No held-out opening, inference, or evaluator call is required.

The training receipt can be modified after checkpoint authorization; the final receipt then binds the modified receipt rather than the receipt that authorized the model.

If a process fails after opening some held-out files but before completing the ledger, a restarted process can open them again.

Smallest safe correction

Use one durable marker and one post-evaluation capability:

Immediately before the first held-out file read, atomically create an O_EXCL marker such as FIXED_FINAL_TEST_OPEN_STARTED.json, binding the run, training receipt hash, and checkpoint hash. Never delete it. If it already exists, refuse to reopen the test content. A failed finalization then permanently fails closed, which is the correct behavior for a strict final test.

Mint a FixedFinalEvidenceCapability only after evaluate_bundle() returns, the test/descriptive result checks pass, and the provenance load receipt has been consumed.

Bind into that capability the exact bundle hash, result hash, opening marker, opening ledger, checkpoint hash, and original training-receipt hash.

Make the raw receipt writer private and require the evidence capability. Re-read the checkpoint and training receipt before writing and require exact equality with the capability records.

This is substantially simpler and more trustworthy than adding more free-standing boolean claims to the receipt.

Overengineering and test-theater assessment
Keep

The committed manifest and exact argument binding.

Exclusive output creation.

Same-file-descriptor checkpoint hash/load.

The single inventory-bound in-memory inference.

The dynamic evaluator authorization and exact fixed-final provenance role profile.

The graph-based distinction between a cyclic corpus and a path-like evaluated segment.

Historical Git-blob validation for already frozen generator sources.

These checks address distinct, decision-critical failure modes.

Simplify or consolidate

Replace boolean temporal claims with one durable marker. A single exclusive TEST_OPEN_STARTED artifact is more meaningful than several booleans asserting that content was not previously opened.

Avoid parallel source-role lists. SOURCE_PATHS in authorization and FIXED_FINAL_CHECKPOINT_ROLE_PATHS in provenance overlap but are independently maintained. Derive both from one canonical fixed-final role map to prevent silent drift.

Replace date-coded protocol roots with a versioned stable root.
